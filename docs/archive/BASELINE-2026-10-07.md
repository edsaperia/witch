# Performance baseline, 2026-10-07 (overnight phase 2)

This baseline was measured on the prototype at #400's merge, before #408 (spacing), in the cloud: 4 cores, Node 22, headless Chromium with a software renderer. It is report only: nothing in the game changes.

**Ed's datapoint.** Seed 871136, wave 28, 40:39 into the run, Old pinewood, over the treetops at (1059, 1499):
- 37 fps on average, 17 fps at the 1% low; frame 25.0 ms median, 41.8 ms at p95.
- CPU 26.6 ms median against GPU 13.4 ms.
- 147 stalls over 100 ms; the worst was 279 ms, in FrameRequestCallback.
- 2,603 wild creatures; sim 183 full / 412 coarse / 1,852 frozen.
- "Enemy marching 3159" is the stack's power, not a count: its biggest stack is 142 creatures.
- Earlier in the same run: 64 fps at wave 12, 57 fps at wave 19.

## How it was measured (tools/bench)

- **`node tools/bench/ts.mjs perf`** (`perf.ts`): the rules alone, headless, on seeds brought to each wave in turn.
  - Brought on as `rules.ts` does: the playtest key, then 3 s of play, again and again.
  - Or `--bot=skilled|champion`: a bot plays at the game's own 300 s waves.
  - Then the same fixed path is flown for 1,800 steps, timing every `stepGame`.
  - Per wave it reports p50/p95/p99/worst, steps over 4 ms and over 16.7 ms, creatures by state, the sim's level of detail (`game.lod`) and the heap.
- **`node tools/bench/late.cjs`**: the built game in headless Chromium on Ed's seed.
  - The rules are brought to wave 28 without drawing, and she's put where Ed was, over the treetops.
  - Then 600 frames are timed at a fixed 1/60 s: 300 hovering, 300 flying north.
  - Each frame records its rules step, its view work by part (`view.ms`), draw calls, what's drawn, and the JS heap.
- **`node tools/bench/ts.mjs spikes`** (`spikes.ts`): a bot game headless. It notes every step over N ms, then profiles exactly those steps by deterministic replay.

**This route is a fair stand-in for Ed's run.** It has about 2,000 wild creatures, more than half frozen, and about 150 marching, against Ed's 2,603 wild, 1,852 frozen and 142 in the big stack.

**The rules' step grows with every creature, frozen ones too.** It goes from about 1 ms at 1,070 creatures to about 3 ms at 2,200. A profile at seed 871136 wave 28 shows why:

| function | share of the rules' time |
|---|---|
| `stepCreaturesNear` | 12% self |
| `stepSpacing`, building its list | 6% self |
| `keepEnragedOut` | 5% self |
| combat (`stepFights`) | 34% inclusive |
| combat (`stepCombat`) | 25% inclusive |

The first three are loops over every creature on every step. At Ed's frame rate (about 1.6 steps a frame) the rules are about **5 ms of his 26.6 ms CPU frame**. They're a real share, but not most of it.

**Bot games at the real 300 s waves don't reach wave 28.** The skilled bot loses at about wave 13 on seed 123 and wave 15 on 871136. The champion loses at wave 19 on 123 and wave 21 on 871136. So the 3 s route above is the late-game benchmark for now.

## 2. A 0.5 s rules stall when the party starts (`spikes`)

On seed 123 (champion), the step where the first wave lands (wave 0 → 1, game time 603 s) takes **514 ms**. Its profile:
- `stepDancefloor` → `stepFloor` → `BOOT_BEATS` → `bootPattern` → `discoPatterns` takes 414 ms.
- Within that, `discoAreaPattern` takes 321 ms, mostly `sigilGlyph` → `inkAt` (277 ms).

The dancefloor's pattern library (`art/dancefloor.js`) is built lazily on the first call, inside a fixed step, the first time the home ring boots: the start of the party. It's cached after that.

**Fix (behaviour unchanged):** build it while the game loads. The next PR does this.

The other steps over 40 ms in that run (60 to 120 ms) were the profiler's and the GC's own pauses, not the rules.

## 3. The late game in the browser (`late.cjs`, seed 871136, wave 28, treetop at (1059, 1499), 1280×720)

At that point: 1,632 creatures, 1,365 wild, 156 marching. Sim 78 full / 352 coarse / 1,172 frozen. 154 draw calls (161 at most), 1,197 trees drawn, nothing dropped.

The cloud's GPU is a software renderer, so the view's `draw` part (about 1.8 s a frame here) is that renderer, not Ed's. Everything else the view does on the CPU each frame, by mean:

| part | ms | | part | ms |
|---|---|---|---|---|
| groundTiles | 1.55 | | prefetch | 0.61 |
| leash | 1.22 | | heightsAhead | 0.43 |
| hud | 0.74 | | party | 0.25 |
| refresh | 0.71 | | grass+lights | 0.24 |
| creatures | 0.68 | | heights | 0.09 |
| witch | 0.64 | | uniforms | 0.08 |
| markers | 0.62 | | the rest | < 0.1 |

That's about 7.4 ms, plus the rules' step at 3.5 ms p50 and 7.2 ms p95. So **about 11 ms of Ed's 26.6 ms is accounted for. The rest is inside `draw` on his machine**: three.js walking the scene, uploading instance buffers and issuing the GL calls. None of that can be timed apart from the rasteriser here. The `?perf=1` HUD (next) will split `draw` into its CPU parts, so we can read it on Ed's machine.

**The JS heap reads about 630 MB in use** (`performance.memory`, 628 MB at the start of the 600 frames, 641 MB at most), and **about 585 MB from the very start of a run** (the `?perf=1` panel, #419). So it's held from load, not built up late.

**Most of it isn't JS objects.** The sampling heap profiler (`HEAP=1 node tools/bench/late.cjs`, from the page's load through wave 28 and 60 frames) finds only **57 MB of objects alive at the end**: 41 MB made in the game's own code, 16 MB native. The rest is most likely the backing stores of typed arrays (the art's pixel data and the ground tiles), which that profiler doesn't count.

A collection's pause grows with the live objects, not with buffers, so **the big heap is probably not what makes Ed's 100 ms stalls**, as first suspected. What does make them is still open. Ed's playtest log (L) records each stall over 100 ms with the frame's parts, and `?perf=1` will show his hitches against the heap's collections.

## What's next

1. **Build the dancefloor's pattern library at load.** This removes the 0.5 s stall when the party starts. It's a small PR and bench-identical.
2. **The `?perf=1` HUD.** Always on, cheap, readable on Ed's machine:
   - frame and CPU p50/p95/p99 and worst, plus the GPU time where the browser gives it;
   - hitches;
   - draw calls;
   - JS heap and its growth;
   - creatures by state and level of detail;
   - `draw` split into its CPU parts.
3. **Ed's stalls.** Read his playtest log's stalls (each with the frame's parts) and `?perf=1` on his machine. The 57 MB of live objects goes to hotel (pooling), and the buffers (which arrays, and whether they're still needed once on the GPU) to foxtrot (hitch hunt).
4. **Creature-count scaling in the rules.** Frozen creatures should cost almost nothing per step: `stepCreaturesNear`, the spacing list and `keepEnragedOut` each visit every creature on every step. Then spacing's thinning (step 2), proved with the bot sweep.
