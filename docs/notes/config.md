# Config files

The link-switch scanner records paths with forward slashes on every OS. Its generated-document check ignores checkout CRLF versus LF only; all text and spacing must still match.

The schema reader's combat data imports `LEGEND` from the pure `rules/creatureLevels.ts`, not the creature simulation. `creatures.ts` retains its original LEGEND/Level exports for callers. The narrow boundary removes the schema tool's runtime import path to creatures/wildWatch/game without changing assembled combat values or any timeout; parity and dependency-graph tests guard it. Windows cold/warm gate timing remains separate evidence, under the laptop allocation rule.

Generated config/docs (A1+A2, Ed's approved architecture review, 2026-10-30): `node tools/config/check.mjs` runs the read-only freshness gates before CI builds the shared game artifact. Failures name the exact repair command. `docs/generated-files.md` inventories each output family, generator, inputs, consumers and policy, including audio/art products that retain their owners' checks and historical evidence that must not be regenerated. The six config/docs families remain committed for GitHub readers and editor/schema contracts. `tools/inventory-notes.json` supplies descriptions for existing headerless tools without changing their owners' source; new headerless tools still fail the inventory check. Inventory/glossary/table checks ignore checkout line endings only.

Tuning formatting: `node tools/config/format.mjs --write` keeps every leaf setting on its own line, arrays of objects in blocks, numeric vectors up to four values inline, and existing key order. `--check` never writes; the formatter refuses any parsed-value change. Only `config/tuning.json` is formatted by this tool. Tuning types: `node tools/config/typegen.mjs --write` derives `src/rules/tuning.generated.d.ts` from the schema (unconstrained nodes retain JSON's inferred type), and `--check` enforces freshness. The validated schema-derived data type must assign to the named public `Tuning` interface; tests/CI validate actual JSON values with full paths, expected types/ranges and allowed choices. There is no startup validator or generation inside typecheck. Derivation found and recorded the existing `light.mood` choices (`spooky`/`plain`); no current knob value changed.

- **Tuning file**: `config/tuning.json`, the numbers Ed edits, and only the numbers (no `_` notes since Ed, 2026-10-28: "Reformat prose into data where you can"; a test fails on one) (speeds, camera, density, glow, pixel size, creatures, bloom, tilt-shift). Its schema is `config/schema/tuning.schema.json` (every knob's type and range; `src/rules/schema.ts` checks it, `src/rules/tuningSchema.test.ts` fails on an unknown, missing, mistyped or out-of-range knob) and its reference, generated from the schema and the knobs' words, is `config/KNOBS.md`. After adding or renaming a knob, or changing its words: `node tools/config/schema.mjs --add --docs` (string choices and name-keyed records go in `TUNING_OVER`, `src/rules/tuningSchema.ts`). Changing a value needs nothing (the reference lists no values). The other configs I check the same way (`combat.json`, `movement.json`, `travel.json`, `area-types.json`: `src/rules/configSchemas.ts` lists each, its records keyed by name and its string choices; `src/rules/configs.test.ts` checks each against `config/schema/<name>.schema.json` and that the species, attacks and area types they name are real). After adding a field to one: `node tools/config/schema.mjs --add` (or `--init` to re-infer every schema).
- **Style file**: `config/style.json`, a style saved in the Witch Art Lab; every sprite is drawn from it.
- **Link switches**: `config/link-switches.json`, every `?name=value` the game reads from its link as a record (its values, what it does in one sentence, its group: run, view, debug or compare-with-old; since when; Ed's decision if any; where it's read), with the families named by a pattern (`d_<id>`) and the retired ones. `docs/LINK-SWITCHES.md` is written from it: after adding, renaming or retiring a switch, edit the record and run `node tools/config/linkSwitches.mjs` (it refreshes each record's `readIn` from the code and rewrites the doc; `--check` only reports). `src/linkSwitches.test.ts` fails on a switch the code reads but the registry lacks, one registered but read nowhere, a stale `readIn` or a stale doc.
- **Knob docs** (Ed, 2026-10-28: "Let's do all the docs work. Reformat prose into data where you can"): what each tuning knob does lives in `config/knobs/<section>.json` (map, forest, witch, army, creatures, legends, party, view, light; `config/knobs/index.json` has the file's own notes and the sections' order), keyed by knob path: `what` (one plain sentence, what it does in player terms: the coordinator's hand pass, 2026-10-28, done for the biggest entries first, the old words moved whole into `notes`; `[n]` marks where decision n was said, in `what` or `notes`), `decisions` (`by`: Ed, Ed's playtest, the coordinator...; `date`; `quote`: his words exactly, one or several; `rest`: what else it said, what it was before), `also` (other knobs the same words cover), `links` (the files it names), `see` (a knob with no words of its own: the one whose words cover it), `notes`. A knob's unit and range are the schema's. Adding a knob: its entry in its section's file (a top-level knob must have one: `src/rules/knobDocs.test.ts`), a decision with Ed's words and the date when there is one, then `node tools/config/schema.mjs --add --docs`, which writes `config/KNOBS.md` and the schema's `description`s (the first sentence of `what`, for an editor's hover) from them (`src/rules/knobDocs.ts`). The files were made from the old notes by `tools/config/knob-docs.mjs` (2026-10-28; it checks every date, quote and word of the notes is kept), which can be re-run on a tuning file that still has notes (`--from`).
